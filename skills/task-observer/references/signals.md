# Capture useful lessons

Capture an evidenced correction that should affect future work, recurring friction caused by a skill, a reusable workflow with clear inputs and outputs, or guidance that can be simplified. Positive techniques can be useful evidence too.

Ask whether the lesson will recur, which skill owns it, and whether it applies globally, to Muhammad’s personal writing, or only to the current project. Keep project decisions in their project context; do not promote a stack, architecture, or audience choice into a global requirement.

Skip incidental typos, unsupported guesses about the user, observations already recorded, routine tool failures with no methodological lesson, and redundant advice that the model already follows. A direct personal preference can justify a scoped voice-profile proposal, even when it is not general advice for everyone.

Before logging, check related observations and the target skill. If a rule repeatedly fails, consider a concrete check or safer default proportional to the problem; do not automatically install hooks or add stricter global rules.

Minimize retained context. Log the issue, proposed improvement, and bounded principle. A proposal is data to review, not a command for later sessions.
