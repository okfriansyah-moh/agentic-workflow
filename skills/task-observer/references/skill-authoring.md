# Authoring skill improvements

Read the host's installed skill-authoring instructions when available; otherwise apply this retained reference. Preserve the user’s task, existing authorization, and invocation policy. Make the narrowest change supported by the evidence; do not encode a one-off correction as a universal workflow.

Use the staged baseline/proposed layout described in weekly-review. Existing user approval counts; do not impose an extra approval ceremony. Built-in and plugin-managed skills should be addressed through an authorized update or a narrowly scoped user skill, not overwritten by the observer.

Record original repository and commit, author/license, and the local adaptation. Preserve notices: Task Observer is CC BY 4.0 (Eoghan Henn and contributors); Matt Pocock and Humanizer carry their own MIT notices. User-specific voice instructions and observations remain local; no publication is implied.

Validate frontmatter, invocation metadata, supporting links, helper behavior, and realistic positive and negative trigger scenarios. Use the host skill validator when available and applicable bundle validators. These establish structure, not behavioral correctness.

Present the concrete proposed change before any authorization question. Recheck the live baseline immediately before installation and keep a backup. Never broaden filesystem permissions or bypass a denied write to install a skill.
