# Selection delivery

Implement the user's complete selection, connect its parts, run relevant checks, obtain one independent review, correct findings, then publish the authorized draft PR. Two tasks receive one combined review; two groups also receive one combined review. Per-task development checks are not separate acceptance reviews.

## Quality and ownership

Keep compilation, typing, lint, dependency boundaries, required behavior/security checks and findings blocking. Preserve 80% changed executable-line coverage, 50 function lines, complexity 10 and nesting 3. Missing tools, empty test selections, stale results and unavailable required observations do not pass. Real database, transport, browser, speech, permission, encryption and recovery obligations retain their required boundaries.

The active coordinator can implement serial work directly in a suitable existing checkout. Keep one selection branch and reuse it for corrections and checks. Add claimed isolated worktrees only for concurrent writers or to protect unrelated work. Serialize shared resources. Combine tested contributions in dependency order before the selection review; composition is not acceptance. A tested predecessor in the selection can support dependent development before its final acceptance. Keep task acceptance pending until the combined review; only the coordinator updates execution fields.

Record the selection once using the shared Git registry. Preserve requested task/group IDs, dependency options, outcome, current branch, PR head and next observable behavior. Omitted resume inputs retain the authorized selection. Do not broaden scope or reset limits on resume. Read the [coordination contract](COORDINATION.md) for command shapes.

## Progress and recovery

Commit recoverable source at natural implementation milestones. At least every 45 minutes during execution record actual changed behavior, relevant check results, local revision, published PR revision, remaining tasks and next action. Captures, hashes, handoffs and support-tool reviews do not count as implemented behavior. If a checkpoint contains only support activity, stop that activity and return to implementation or diagnosis of the real blocker. If nothing selected can proceed, report the blocker promptly.

Optional capture/evidence-tool repair has one cumulative selection-wide budget: two focused attempts or 20 minutes, whichever comes first. Account for an open repair when resuming. Different phases, branches, agents and renamed work groups share that budget. Once exhausted, stop optional repair and use a simpler sufficient observation or defer optional media. A real product, security or accessibility defect remains blocking and is fixed as implementation work. Keep the configured two-failed-correction limit for required failures; do not start equivalent renamed repair groups. Continue independent selected work when ownership and dependencies permit it.

“Finish and wrap up” expresses urgency to complete the goal. Stop execution when the user explicitly asks to stop. Standing authorization continues to cover its established scope; do not repeatedly ask permission for covered recovery, commands or delivery.

## Checks and evidence

Use the existing gate registry and actual runners. Select changed components and dependent consumers; shared build/contract changes require broader checks. Run each distinct check once per valid input set. Reuse results only with matching source/tests, configuration, command, toolchain, environment, artifact integrity and applicable scanner freshness. Rerun affected checks after corrections; a whole-repository percentage is not changed-line coverage. CI and hooks use the same definitions. Hook feedback does not replace final verification.

Keep one compact selection record, one findings ledger and linked runner results, with commands, exits, counts, source inputs and reviewer identity. Avoid duplicate manual receipts and handoffs. Routine browser cases can use assertions and direct inspection; screenshots support visual inspection when needed. Record video/audio only when required by the observation or requested by the user. An actual speech obligation needs actual reader observation: DOM, audio energy or a missing recording cannot establish an announcement.

Exhaustive visual/theme/width/browser matrices, assistive-technology sweeps and media provenance belong to their release owners unless the selected feature requires that exact observation. Reassign deferred proof explicitly without deleting requirements or marking them passed. Known keyboard/browser regressions and necessary working paths in each promised client remain required. Avoid custom recorders and demonstration applications when the real feature and existing runners suffice.

## Review and publication

One independent reviewer inspects the full selection's requirements, interactions, contracts, tests, correctness, security and relevant accessibility. Incorporate specialist scrutiny in that review when warranted. A worker's self-review is not final independent review. Correct findings in the same branch/ledger; review the fixes and rerun affected checks without restarting unrelated reviews. Publication requires current passing checks, no unresolved required findings and acceptance of the entire selection at the reviewed inputs.

Distinguish local implementation, checks, accepted review and published source in every delivery update. State the local and PR revisions and whether a PR update changed commits or only title/description. A successful capture command is provisional until its observations are inspected. Publication after review means the PR may remain unchanged during implementation; say so explicitly. Do not imply unimplemented tasks are nearly delivered.

Preserve stopped work and diagnose real findings before resuming it. Installing this workflow does not resume any application task. Measure implementation, checks, coordination, review, capture time and available input/output token counters for completed selections before forecasting later groups. Missing proof or unresolved failures never count as a speed improvement.
