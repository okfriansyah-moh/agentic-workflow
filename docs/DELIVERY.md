# One implementation workflow

This policy governs Codex, Cursor AI, Claude Code and GitHub Copilot. Every entry point follows one procedure: **read the approved outcome → implement → run agreed affected checks → obtain one independent combined review → correct findings → deliver**. There are no workflow tiers or alternate completion rules. Start/resume are lifecycle actions, delivery values are destinations, and delegation assigns responsibility within this procedure. CLI `--stage` values select check sets, not workflows.

## Approved outcome and direct implementation

Use the approved plan or chat brief. It identifies outcome and exclusions; the full journey including success, return destination, retained context and relevant failures; approved visual references, components, tokens, assets, states and sizes; allowed changes and protected files; dependencies/interfaces; agreed checks and delivery destination. Link precise references instead of copying source packages. Resolve material contradictions during planning. Latest explicit user instructions govern; routine choices follow project conventions.

The current chat coordinates and implements serially in one suitable checkout by default. Load only guidance needed by the selected work. Protect workflow code, bundled skills, agent definitions, gate policy and unplanned Python files during product work. Harness maintenance requires a separate requested task. Continue approved implementation without regenerating plans, renumbering tasks, revising unrelated docs or reopening design exploration. New user constraints update the affected selection without resetting its history.

Use scoped optional workers for separable contributions, with isolated worktrees/resources for concurrent writers. No nested coordinator or automatic specialist roster. Combine tested contributions in dependency order; composition remains pending final review. Only the coordinator updates task execution fields after acceptance. Preserve task IDs and unrelated work.

For changed UI, open the actual approved reference. Implement a representative screen/state and compare it before propagating shared styling. Match layout, density, typography, colors, assets, controls and states at agreed sizes and comparable rendering conditions. Complete the journey through progress, confirmed success, return and retained context. Correct differences before delivery. Appearance and behavior need separate observations; claim pixel identity only when an actual comparison supports it. An unavailable observation stays unverified.

## Checks and evidence

Use the existing gate registry and actual runners. Select changed components and dependent consumers from the agreed baseline; shared contracts/build inputs retain necessary broader checks. Documentation edits do not launch application suites. Unknown executable ownership or an invalid baseline requires an explained conservative selection. Managed edit hooks emit notifications only and never run check commands; retained legacy hook settings do not change this. Deduplicate explicit check commands and run each once per valid input set. Reuse requires matching source/tests, configuration, command, toolchain/environment and retained artifacts; rerun affected checks after corrections.

Preserve project quality/security rules and real proof boundaries. Movie-app requires 80% changed executable-line coverage, 50 function lines, complexity 10 and nesting 3; other projects retain their configured thresholds. Missing tools, empty test selections, stale reports and unobserved required boundaries do not pass. Keep necessary real database, transport, browser, permission, encryption, recovery and reader observations.

Explicit no-test instructions apply within this workflow: add and run no tests, including hook-triggered tests, and perform no hidden browser trials. Obtain independent source review and disclose verification limits. Unrun required checks remain pending; source review is not runtime acceptance. Authorized draft publication can disclose these limits without marking them passed. Merge/release claims remain subject to applicable requirements. Never weaken a gate to manufacture success.

Use one compact selection record, one findings ledger and linked runner results. Routine UI work uses focused assertions/direct inspection. Media, exhaustive matrices and separate evidence audits activate only when required by selected behavior or requested. An actual speech claim requires reader observation; DOM or audio-energy output is insufficient. Do not build capture frameworks when existing tools suffice. See [gates](GATES.md) for checks and [coordination](COORDINATION.md) for helper contracts.

## Review and delivery

One independent reviewer inspects the whole selection after implementation/composition: requirements, visual references, complete journeys, standards, correctness, contracts, actual checks, relevant security and accessibility. Add specialist scrutiny within that review only when necessary. Implementer self-review is not independent review. When a host cannot invoke a separate supported reviewer, leave review pending rather than claim acceptance.

Correct findings in the same branch and ledger. Review fixes and rerun affected checks without restarting unrelated reviews. Publication requires accepted review and current required checks, except an explicitly authorized draft that clearly discloses pending verification. Report implementation, checks, review and published source separately, including local/PR heads and metadata-only PR edits. A successful capture command remains provisional until inspected. Installation never resumes application work.

## Progress, recovery and cross-host resume

Record the selection once in Git-shared state: outcome, IDs, dependency options, constraints, check contracts, branch/worktree, owner, PR head and next action. Resume on any host restores that state, valid results, findings and limits; conversational memory does not transfer. Explicit resume inputs override retained values; missing inputs do not broaden scope. Transfer ownership before another coordinator mutates the selection.

Commit recoverable product changes at natural milestones. At least every 45 minutes record actual changed behavior, relevant checks, local/published revisions, remaining work and next action. Support-only activity triggers a return to implementation or the real blocker. Optional evidence-tool repair shares two attempts or 20 minutes across the selection, including open attempts and host switches. Preserve the configured required-correction limit; branches, workers and renamed phases do not reset it. Continue independent selected work or report the precise blocker.

Honor standing authorization within scope; host trust, permissions and organization policy remain separate controls. An explicit stop stops execution. Measure time/token counters only when available; missing proof never counts as a speed improvement. Create no monitoring automation as part of this workflow.
